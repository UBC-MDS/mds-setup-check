# Working in this repository

Context for an agent. Nobody reads this file for pleasure, so it carries the detail the
reader-facing documents deliberately shed.

## What this is

CI that tests whether the UBC MDS install instructions still work.

The **source of truth is the install guides**, at `UBC-MDS/UBC-MDS.github.io` under
`content/resources_pages/`: `install_ds_stack_mac.md`, `install_ds_stack_ubuntu.md`,
`install_ds_stack_windows.md`. Students follow those. This repository does not define
the stack -- it reproduces the guides and measures whether following them produces a
working setup.

Three files here are served to students by GitHub Pages straight from `main`, so
editing them changes what students run **today**, with no deploy step:

```
check-setup-mds.sh        the setup check students run at the end of installation
check-python-installs.sh  run before installing uv, and again from inside the above
mds-help.sh               the `mds-help` reference card
```

## The one rule

**A deviation from the guides must be a CI-only artifact, or it is a bug.**

When something here has to differ from what a student does, that difference has to be
explained by a property of a GitHub runner -- not by convenience. If a workaround
exists because the *tool* is broken, then a student hits it too, and the guides have to
say so. Two of these were found by shipping: a fixture renamed everywhere except in the
script students run, and a fixture whose image the script never copied. Both survived
because nothing exercised the student path. That is now covered end to end in CI.

Anything genuinely unfixable is recorded in `KNOWN_TO_FAIL` in `ci/assert-renders.py`,
with its cause, and it fails the build if it ever *starts* working.

**Also keep this repo in sync with the install guides.** When a change here implies a
change there, say so and offer the guide edit; a fix that lands only in the tested half
is exactly the failure mode above.

## Documentation style -- read before editing any .md

The docs were long and nobody read them. They were cut hard in August 2026 and must
stay that way.

- **Length is a defect, not thoroughness.** If a section is growing, the detail belongs
  in this file instead.
- **Student-facing content goes at the top, under a `## For students` heading.**
  Instructor and maintainer content follows it.
- **Prefer numbered steps** to prose whenever the reader is trying to accomplish
  something.
- **Prose here does not use em dashes**; `--` is used instead, matching the existing
  files.
- **Cross-reference a section by linking to it, never by writing "§4" or "see section
  4".** A number survives a rename and quietly points at the wrong place; a link breaks,
  and `make check-docs` fails the build when it does. Anchors follow GitHub's rule --
  lowercase, punctuation dropped, spaces hyphened -- so `## 6. Autograding and Docker`
  is `#6-autograding-and-docker`.
- The route matrix lives in `docs/render-matrix.md`, not in the README. It is
  intimidating and it is generated, so it does not belong in the front door.
- `README.md`, `mds-demo-assignment/README.md` and everything in `docs/` are the
  reader-facing set. This file is not. Longer-form guides live in `docs/`; the README
  is the front door and stays short.

## The three commands

```bash
make install    # Python via uv, R via renv, and the browser the WebPDF route needs
make all        # render every document by every route
make check      # the verdict
```

`make all` wraps the render in `-k` and ignores the exit code on purpose: one route is
known not to work, and stopping there would leave every later route unrendered and
looking broken. CI calls the inner `render` target so those two flags stay visible in
the workflow. **`make check` is the verdict, never make's exit code.**

Run `make` alone for the full target list; it is generated from the `##` comments.

## What makes a check real

This repo exists because *rendering without an error is not the same as rendering
correctly*. Every LaTeX route exits 0 while silently dropping characters it has no
glyph for. So:

- **Assert on content, never on exit codes or file existence.**
- **A check must be able to fail.** Three could not, because the string they searched
  for also appeared in the prose beside the construct being tested -- `"unbiased"` next
  to the inline equation, `σ` in a table two sections below the numbered equation.
  Needles must exist *only* inside the thing under test. `OLS`, `RSS`, `Var`, `MSE` are
  chosen that way.
- **A needle must survive PDF text extraction, not merely be unique.** One marker began
  as `RAWFN`, which renders correctly and extracts from the LaTeX PDF as `RA WFN`,
  because lualatex kerns the `AW` pair and pypdf reports the kern as a space. The check
  failed on content demonstrably on the page. It is now `RTFN`.
- **Measure, do not assert.** The matrix in `docs/render-matrix.md` is generated by
  `ci/feature-matrix.py` and diffed against the committed block by `make matrix-check`.
  Never hand-edit it.
- **One source of truth per fact.** `ci/feature-matrix.py` derives its routes *and* its
  features from `ci/assert-renders.py`. They used to be two hand-kept lists and drifted.

Checks are gated on what each source document actually contains, so a fixture is only
asked about constructs it holds. A new fixture needs no special case.

## The fixtures

**Everything the fixtures need, and everything they produce, lives in
`render-checks/`.** The repository root holds the three scripts GitHub Pages serves and
little else.

Each renderer is told an output name WITHOUT a directory, because each resolves it
relative to its input: `quarto render render-checks/x.ipynb --output NAME` writes NAME
to the *working* directory, and `--output-dir` separates a document from its `_files/`
sidecar and yields a stylesheet-less HTML that every content check still passes.
`-M output-file:` is the form that works. `ci/webpdf.py` is the one exception and takes
a full path, because it writes where it is told.

The directory is joined in exactly one place, `fixture()` in `ci/assert-renders.py`,
and every other script imports it. `ROUTES` and `KNOWN_TO_FAIL` keep bare filenames,
because those are the labels the matrix table and the failure prose read.

Output files are named `<document>-<tool>-<format>`. This is load-bearing, not cosmetic:
Quarto compiles to an intermediate named after the *input* and then moves it, so a
route named after its input alone gets silently eaten by the next route.

**Fixtures are organised by input format, because that is the choice an instructor
makes first and cannot easily undo.** Four full fixtures carry the same features -- two
`.qmd` (one per language kernel), one `.ipynb`, one `.Rmd` -- so any difference between
them is a property of the toolchain rather than of the document. Someone asking "I have
a notebook; what can I do with it?" should find the answer in one file.

**The rule for splitting a construct out is whether it KILLS the render, not whether it
fails.** A construct that renders wrong but exits 0 belongs in the full fixtures: it
gets its own column, and the column is the attribution. A construct that stops the
render takes every other construct in that file down with it, so it has to be alone.

`check-notebook-table.ipynb` is the only one that qualifies. nbconvert cannot export a
notebook containing a markdown table -- it produces *no file at all* -- which made the
route students actually use fail for everyone. With the table in its own file, the
matrix says both things at once, and the row turns green the day upstream fixes it.
Three routes over that one table locate the fault: nbconvert's HTML is fine, Quarto's
LaTeX is fine, so it is nbconvert's LaTeX template.

There used to be a second isolated fixture, holding the constructs pandoc forwards
rather than parses (it is in the history if you need the name). It was retired because
its constructs render without killing anything -- per-construct columns already give
the attribution its isolation provided -- and because it was organised by *mechanism*,
which asks a reader to know pandoc has a parser before they can find out whether they
may write an equation. Its contents now live in all four full fixtures. Naming a
retired file here is itself caught by `make check-docs`, which is why this paragraph
does not.

Note the fixtures are not empty files. An empty notebook has no markdown cells, so
rendering one never calls pandoc and passes on machines where PDF export of a real
assignment would fail.

## The student script

`check-setup-mds.sh` has properties that are easy to break and that matter:

- **Both prompts are guarded by `[ -t 0 ]`** and default to no. That is what stops a
  piped or scheduled run recording a student's environment. CI answers them through a
  real pty (`ci/run-setup-check.py`); feeding one from a pipe misaligns the answers.
- **Consent, not just redaction.** The log is mailed to instructors. Nothing goes in it
  that the student was not shown on screen first -- so everything is written *before*
  the dump at the end, and anything after it must use `tee`.
- **Everything that can hold a credential goes through `redact_secrets`**, including
  `env`. Note `pat` is matched as a whole word only; as a substring it is inside `PATH`.
- **Deleting the student's folder is their decision**, asked as its own question,
  defaulting to no, with two guards in front of the `rm -rf`.
- **RStudio and Positron are the only two `MISSING` lines a student may ignore.** They
  are the only programs checked that nobody runs from a terminal, so if the application
  opens, the lookup was wrong and nothing is broken; every other name there is a command
  the student will type, `docker` included. The script says so in a note under that
  section, and `report_missing` writes the line and records the name in one call --
  grepping the finished log for the two names instead would switch the note off silently
  the day a requirement string is reworded. CI asserts the note appears whenever those
  lines do.
- Windows is detected from `uname -s` (`MINGW*`, `MSYS*`, `CYGWIN*`) with `OSTYPE` as a
  second opinion. Testing `OSTYPE=msys` alone broke every Windows check the day Git Bash
  started reporting `cygwin`, sending them down the Linux branch.
- The `2> /dev/null` idiom is how a fixture rename went unnoticed for three commits. Do
  not silence a copy that is meant to be load-bearing.

## Keeping things in sync

`make check-docs` (`ci/assert-docs.py`, also run in CI) enforces the mechanical half:
every `make` target, fixture and `ci/` script named in `README.md`, `CLAUDE.md` or
any document in `docs/` has to exist, and every relative link in them resolves --
file *and* heading. Add a new reader-facing document to `DOCS` in that script.

`make check-contract` (`ci/assert-contract.py`) is the separate gate for the claims
`docs/assignment-workflow-uv.md` makes about this repo's own `pyproject.toml` and
routes. It
groups its output under that document's **headings**, not its section numbers, so
renumbering the guide cannot strand it.

Neither can check whether the prose is *true*, so when behaviour changes, update the
document in the same commit.

**`mds-demo-assignment/DSCI_521_LAB_ORIENTATION_*/` are build output, not sources.**
`package-assignment.py` deletes and recreates them on every `make all`, so an edit made
there is reverted by the next build and nothing says so. The edit belongs in
`source/<lab>/` or in `student-template/<kind>/`. Nothing checks this, and it has now
been got wrong twice: `bd03691` fixed the R ignore rules only in the handout, and
`7137844` rewrote a paragraph of `lab0b.Rmd` only in the handout. Both were recovered
by hand. If you regenerate and a handout comes back changed, that is an edit somebody
lost, not noise -- port it to the source before committing.

## Deliberate choices that look accidental

- `ipykernel` is a real dependency, not a dev dependency. `jupyterlab` would pull it in
  anyway, but an autograding image built with `uv sync --no-dev` would then have no
  Python kernel at all.
- `nbconvert[webpdf]` is named explicitly. `otter-grader` already requires it, but
  naming it records that MDS depends on WebPDF export directly.
- `check-rmarkdown.Rmd` asks for `latex_engine: xelatex`. R Markdown's default pdflatex
  cannot typeset the accented characters that turn up in real student work, and it fails
  with an error that does not obviously point at the engine.
- R and Python live in separate fixtures. Putting both in one would need `reticulate` to
  locate this project's Python from inside R, which goes wrong often enough not to be
  worth meeting in week one.
- `renv.lock` uses implicit snapshots, so it records only the packages the documents
  here actually use. It previously used `snapshot.type: "all"`, which pulled in the
  fifteen base and recommended packages that ship with R -- invisible on a machine that
  has them, a hard failure on one that does not: a fresh macOS runner tried to compile
  `rpart`, `Matrix` and `nlme` from source and died on a missing header.
- The R repository is Posit Package Manager, not CRAN. CRAN publishes no Linux binaries,
  so an Ubuntu student compiles every R package from source; P3M serves them pre-built.
- `renv.lock` is **not** a copy of the R packages the install guides ask students to
  install globally. Those are verified separately by the setup check, against the user
  library. Two different questions: "does your machine have the MDS R stack" and "can
  this project install its own R packages reproducibly".
- The R version in `renv.lock` matches the install guides. renv warns, but proceeds, on
  a different minor version.
- The handout `.Rproj` is called `assignment.Rproj` in **every** assignment, and is
  copied under that name rather than renamed to match the folder. Two facts in the
  RStudio source make the fixed name free, and both were checked rather than assumed:
  `ProjectPopupMenu.getProjectDisplayName()` falls through to `ProjectMRUList`, which
  builds its label from `getParentPathString()`, so the toolbar shows the *directory*
  (`DSCI_521_LAB1_USERNAME`, which is what a student wants to see) and never the file
  stem; and rstudio/rstudio#4387, in 1.2, changed opening a directory to "use an .Rproj
  in the directory if we can, regardless of its name" instead of writing a second one.
  Before that fix a mismatched name really did produce duplicate project files, which is
  where the folklore about matching them comes from. An instructor who wants a label
  other than the folder name can set `ProjectName:` in the file: it is the `project_name`
  user pref, "User-provided name for the currently opened R project", and it takes
  priority over the MRU label. It is deliberately not in the template, because setting it
  is per-assignment work and leaving it generic would label every lab the same.
- `.gitignore` and `Makefile` live in `student-template/<kind>/`, not in the `workspace`
  list `package-assignment.py` copies from `mds-demo-assignment/`. They are the files
  that genuinely differ by language, and keeping the ignore rules in the shared list is
  how they came to be hand-edited into a generated directory. `spec["template"]` names
  the required files, so a rename fails the build rather than shipping a handout with no
  `.gitignore` in it.
- The handout ignore rules are github/gitignore's `R.gitignore` and `Python.gitignore`
  verbatim, below an MDS block, with one deletion: `vignettes/*.html` and
  `vignettes/*.pdf` are dropped from the R one, because a rendered document is the
  submission here. `docs/` is deliberately **kept**, even though it means an R lab
  cannot ship a folder by that name -- it is upstream's pkgdown rule, and the point of
  pasting the file verbatim is that it stays recognisable as the upstream file.
  `mds-demo-assignment/.gitignore` is now the instructor's alone; it still ignores
  `*.pdf` and `*.html`, which is what keeps the demo's own renders out of *this*
  repository, and it never reaches a student.

## What a green build does not prove

Kept short in the README; the full list:

- The student script runs end to end on all three platforms, but **nothing asserts that
  a `MISSING` line is right.** The follow-up step greps for five specific strings; no
  version pattern is compared against a real install.
- **The version patterns are substring tests.** `R=4.*` accepts `R version 5.0.0
  (2027-04-20)` -- it matches the `04` in the date. `latex=3.*` cannot fail at all,
  because pdfTeX's version string is π. Issue #7.
- **The R packages the guides ask for are installed by nothing here:** `tidyverse`,
  `janitor`, `gapminder`, `readxl`, `usethis`, `devtools`, `languageserver`, and -- most
  fragile -- `ottr` and `canlang`, which install from git HEAD and can break with nobody
  touching anything.
- **Several programs are never installed on a runner**, so their checks are exercised
  nowhere: Positron, RStudio, PostgreSQL, Docker, XQuartz, Rtools.
- **The Python packages section cannot fail for anything a student did.** The script
  clones this repo, runs `uv sync` against the committed `uv.lock`, and reports the
  versions it just installed. It proves `uv` works and the network was reachable.
- **TinyTeX is installed by a GitHub action**, not by the `tinytex::install_tinytex()`
  route plus logout that the guides give students -- so the PATH step they warn about is
  verified on no platform. The 22-package `tlmgr` list *is* checked and does match.
- **`check-python-installs.sh` is fetched over HTTP at run time.** CI serves the branch
  under test on `127.0.0.1:8127` so a pull request tests its own copy; without that it
  would test the published one.
- On Windows the end-to-end run has no pty (Python's pty is Unix-only), so both prompts
  take their default of no and the Python and document-export sections never run there.
  The platform branch and system-program checks do.

## Conventions

- Commit messages explain *why*, and are the record of what was learned. They are used
  as evidence when reconstructing a decision.
- Issues and pull requests carry a `From Human:` section first, then `---`, then
  `From Claude:`.
- Open work lives in GitHub issues on this repo, not in a design document. There used to
  be a spec at `docs/superpowers/specs/`; it went stale in three separate ways and was
  removed. Its still-open items are issues #7 and #18.
