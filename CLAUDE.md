# Working in this repository

## What this is

CI that tests whether the UBC MDS install instructions still work.

The **source of truth is the install guides**, at
`UBC-MDS/UBC-MDS.github.io` under `content/resources_pages/`:
`install_ds_stack_mac.md`, `install_ds_stack_ubuntu.md`, `install_ds_stack_windows.md`.
Students follow those. This repository does not define the stack — it reproduces the
guides and measures whether following them produces a working setup.

Three of the files here are served to students by GitHub Pages straight from `main`, so
editing them changes what students run **today**, with no deploy step:

```
check-setup-mds.sh        the setup check students run at the end of installation
check-python-installs.sh  run before installing uv, and again from inside the above
mds-help.sh               the `mds-help` reference card
```

## The one rule

**A deviation from the guides must be a CI-only artifact, or it is a bug.**

When something here has to differ from what a student does, that difference has to be
explained by a property of a GitHub runner — not by convenience. If a workaround exists
because the *tool* is broken, then a student hits it too, and the guides have to say so.
Two of these were found by shipping: a fixture renamed everywhere except in the script
students run, and a fixture whose image the script never copied. Both survived because
nothing exercised the student path. That is now covered end to end in CI.

Anything genuinely unfixable is recorded in `KNOWN_TO_FAIL` in `ci/assert-renders.py`,
with its cause, and it fails the build if it ever *starts* working.

## The three commands

```bash
make install    # Python via uv, R via renv, and the browser the WebPDF route needs
make all        # render every document by every route
make check      # the verdict
```

`make all` wraps the render in `-k` and ignores the exit code on purpose: one route is
known not to work, and stopping there would leave every later route unrendered and
looking broken. CI calls the inner `render` target so those two flags stay visible in
the workflow. **`make check` is the verdict, never make's exit code.**

Run `make` alone for the full target list; it is generated from the `##` comments.

## What makes a check real

This repo exists because *rendering without an error is not the same as rendering
correctly*. Every LaTeX route exits 0 while silently dropping characters it has no glyph
for. So:

- **Assert on content, never on exit codes or file existence.**
- **A check must be able to fail.** Three could not, because the string they searched for
  also appeared in the prose beside the construct being tested — `"unbiased"` next to the
  inline equation, `σ` in a table two sections below the numbered equation. Needles must
  exist *only* inside the thing under test. `OLS`, `RSS`, `Var`, `MSE` are chosen that way.
- **Measure, do not assert.** The README's route matrix is generated by
  `ci/feature-matrix.py` and diffed against the committed block by `make matrix-check`.
  Never hand-edit it.
- **One source of truth per fact.** `ci/feature-matrix.py` derives its routes *and* its
  features from `ci/assert-renders.py`. They used to be two hand-kept lists and drifted.

Checks are gated on what each source document actually contains, so a fixture is only
asked about constructs it holds. A new fixture needs no special case.

## The fixtures

**Fixtures are organised by input format, because that is the choice an instructor
makes first and cannot easily undo.** Four full fixtures carry the same features --
two `.qmd` (one per language kernel), one `.ipynb`, one `.Rmd` -- so any difference
between them is a property of the toolchain rather than of the document. Someone
asking "I have a notebook; what can I do with it?" should find the answer in one
file, not assembled from several.

**The rule for splitting a construct out is whether it KILLS the render, not whether
it fails.** A construct that renders wrong but exits 0 belongs in the full fixtures:
it gets its own column, and the column is the attribution. A construct that stops the
render takes every other construct in that file down with it, so it has to be alone.

`check-notebook-table.ipynb` is the only one that qualifies. nbconvert cannot export a
notebook containing a markdown table -- it produces *no file at all* -- which made the
route students actually use fail for everyone. With the table in its own file, the
matrix says both things at once — the notebook route works, *and* this is what breaks
it — and the row turns green the day upstream fixes it. Three routes over that one
table locate the fault: nbconvert's HTML is fine, Quarto's LaTeX is fine, so it is
nbconvert's LaTeX template.

There used to be a second isolated fixture, holding the constructs pandoc forwards
rather than parses (it is in the history if you need the name). It was retired for two
reasons. Its constructs render without killing anything, so per-construct columns
already gave the attribution its isolation was meant to provide. And it was organised
by *mechanism* -- "things pandoc forwards" -- which asks a reader to know pandoc has a
parser before they can find out whether they may write an equation. Its contents now
live in all four full fixtures, where the question that leads to them is the one being
asked. Note that naming a retired file here is itself caught by `make check-docs`,
which is why this paragraph does not.

One thing that fixture taught before it went, which applies to every needle here: **a
needle must
survive PDF text extraction, not merely be unique.** Its marker began as `RAWFN`, which
renders correctly and extracts from the LaTeX PDF as `RA WFN`, because lualatex kerns
the `AW` pair and pypdf reports the kern as a space. The check failed on content that
was demonstrably on the page. It is now `RTFN`.

Output files are named `<document>-<tool>-<format>`. This is load-bearing, not cosmetic:
Quarto compiles to an intermediate named after the *input* and then moves it, so a route
named after its input alone gets silently eaten by the next route.

## The student script

`check-setup-mds.sh` has properties that are easy to break and that matter:

- **Both prompts are guarded by `[ -t 0 ]`** and default to no. That is what stops a
  piped or scheduled run recording a student's environment. CI answers them through a
  real pty (`ci/run-setup-check.py`); feeding one from a pipe misaligns the answers.
- **Consent, not just redaction.** The log is mailed to instructors. Nothing goes in it
  that the student was not shown on screen first — so everything is written *before* the
  dump at the end, and anything after it must use `tee`.
- **Everything that can hold a credential goes through `redact_secrets`**, including
  `env`. Note `pat` is matched as a whole word only; as a substring it is inside `PATH`.
- **Deleting the student's folder is their decision**, asked as its own question,
  defaulting to no, with two guards in front of the `rm -rf`.
- **RStudio and Positron are the only two `MISSING` lines a student may ignore.** They
  are the only programs checked that nobody runs from a terminal, so if the application
  opens, the lookup was wrong and nothing is broken; every other name there is a command
  the student will type, `docker` included. The script says so in a note under that
  section, and `report_missing` writes the line and records the name in one call —
  grepping the finished log for the two names instead would switch the note off silently
  the day a requirement string is reworded. CI asserts the note appears whenever those
  lines do.
- The `2> /dev/null` idiom is how a fixture rename went unnoticed for three commits.
  Do not silence a copy that is meant to be load-bearing.

## Keeping things in sync

`CLAUDE.md`, `README.md`, `assignment-workflow-uv.md` and the repository must agree.
`make check-docs` (also run in CI, via `ci/assert-docs.py`) enforces the mechanical
part: every `make` target, fixture and `ci/` script named in any of the three has to
exist. `make check-contract` (`ci/assert-contract.py`) is the separate gate for the
claims the assignment guide makes about this repo's own `pyproject.toml` and routes;
it used to run only in CI, where an instructor copying this repo could not reach it. It cannot check whether the prose
is *true*, so when behaviour changes, update both documents in the same commit.

The README is written for students and instructors; this file is context for an agent.
Where they overlap — the three commands, the known limitations — they must not disagree.

**Also keep this repo in sync with the install guides.** When a change here implies a
change there, say so and offer the guide edit; a fix that lands only in the tested half
is exactly the failure mode described under "The one rule".

## Conventions

- Commit messages explain *why*, and are the record of what was learned. They are used as
  evidence when reconstructing a decision.
- Prose here does not use em dashes; `--` is used instead, matching the existing files.
- Issues and pull requests carry a `From Human:` section first, then `---`, then
  `From Claude:`.
- Open work lives in GitHub issues on this repo, not in a design document. There used to
  be a spec at `docs/superpowers/specs/`; it went stale in three separate ways and was
  removed. Its still-open items are issues #7 and #18.
